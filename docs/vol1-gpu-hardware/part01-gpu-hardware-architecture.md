# 第一部分 GPU 体系结构基础（为什么 GPU 能够快）

> **本部分约定：完全不出现 CUDA 代码。** 目标只有一个——理解 GPU 硬件本身为什么长成今天这个样子。如果你跳过这部分直接学 CUDA API，你会把很多"人为设计"误认为"随意设计"，比如"为什么 Warp 恰好是 32 线程"这种问题会一直困扰你。

## 第一章 GPU 体系结构

### 1.1 CPU vs GPU：两种完全不同的设计哲学

#### 1.1.1 出发点不同：延迟优化 vs 吞吐量优化

CPU 和 GPU 从诞生第一天起就是为了解决不同的问题：

- **CPU（Latency Processor，延迟优化处理器）**：目标是让**单个任务尽快完成**。它面对的是分支密集、依赖链复杂、访存模式不可预测的通用程序（操作系统、数据库、浏览器……）。
- **GPU（Throughput Processor，吞吐量优化处理器）**：目标是让**海量同构任务的总完成时间最短**，单个任务多花点时间没关系，只要整体吞吐量够高。它最初面对的是像素着色这种"每个像素做一样的事，但有几百万个像素"的任务。

这个出发点的不同，直接决定了芯片面积怎么分配。一颗芯片的晶体管预算是有限的，CPU 和 GPU 把这些晶体管花在了完全不同的地方：

```
CPU 晶体管预算大头：
┌─────────────────────────────┐
│  乱序执行 (OoO) 逻辑          │  ← 让单线程尽快跑完
│  分支预测器                   │
│  超大 Cache（L1/L2/L3）        │  ← 用缓存换低延迟
│  少量但极强的 ALU              │
└─────────────────────────────┘

GPU 晶体管预算大头：
┌─────────────────────────────┐
│  海量简单 ALU（CUDA Core）      │  ← 堆算力
│  大寄存器堆（每线程独占一份寄存器）│  ← 用寄存器换切换开销
│  轻量硬件线程调度器（Warp Scheduler）│
│  少量 Cache，主要靠带宽和并行掩盖延迟│
└─────────────────────────────┘
```

一个直观的数字对比（以 CPU 桌面级 8 核 vs 同代高端 GPU 为例，量级参考）：

| 维度 | CPU | GPU |
|---|---|---|
| 核心数量 | 个位数~几十 | 上万个 ALU（分布在上百个 SM 中） |
| 单核心时钟频率 | 高（~4-5GHz） | 较低（~1.5-2GHz） |
| 单线程延迟优化 | 强（乱序执行、分支预测、大 Cache） | 几乎没有（顺序执行、简单流水线） |
| 并发线程数 | 几十（超线程） | 数万甚至数十万（同时驻留） |
| 设计目标 | 让 1 个任务尽快完成 | 让 N 个任务总吞吐最大 |

#### 1.1.2 为什么 GPU 适合并行计算

关键洞察：**延迟（Latency）和吞吐量（Throughput）是可以互相转换的资源，但转换方式不同。**

CPU 应对"访存慢"这个问题的方式是**降低延迟**：用大 Cache 让数据尽量命中在片上、用乱序执行把等待时间"填"上其它无关指令。这种方式对芯片面积的"性价比"很低——Cache 越大，命中率提升的边际收益越小。

GPU 应对"访存慢"这个问题的方式是**隐藏延迟（Latency Hiding）而不是降低延迟**：一个内存请求发出后需要等待几百个时钟周期才能返回，GPU 不会让硬件闲着等，而是立刻切换去执行另一个已经就绪的线程。只要"同时在飞"的线程足够多，总有一个线程的数据已经准备好可以执行，从而把等待时间完全掩盖掉。这就是为什么 GPU 需要**海量线程**——线程数量本身就是用来掩盖延迟的资源，而不仅仅是为了"多干活"。

这也解释了一个常见误解：GPU 单个线程其实比 CPU 单个线程慢得多（频率低、无乱序执行、无分支预测），GPU 快是因为**总吞吐量**，代价是**用并行度换延迟隐藏**，而不是每个线程本身跑得快。

能够被 GPU 加速的问题通常有一个共同特征——**数据并行（Data Parallelism）**：同一段代码，作用在大量互相独立（或依赖关系规整）的数据上。图形渲染中每个像素、深度学习中每个矩阵元素、科学计算中网格里的每个格点，都是这种模式。反过来，强依赖链、大量不可预测分支的任务（比如解析一段有复杂语法的文本）天生不适合 GPU。

#### 1.1.3 SIMD：单指令流多数据流

SIMD（Single Instruction Multiple Data）是**数据级并行**最经典的实现方式：一条指令同时对一组数据做相同的运算。

```
标量指令:  c = a + b                       （1 次运算）

SIMD 指令: c[0..7] = a[0..7] + b[0..7]      （1 条指令，8 次运算）
```

CPU 的 SSE/AVX/AVX-512 就是 SIMD：一个执行单元内部有多路 ALU，一条指令驱动多路数据同时计算，指令译码、取指、发射的开销被"摊薄"到多个数据上。SIMD 的本质是**指令级的数据并行**，编译器或程序员需要显式地把数据打包成向量（vectorize）。

SIMD 的局限：向量宽度是固定的（比如 AVX-512 是 512 位/16 个 float），如果分支导致向量内部分数据需要走不同路径，要么退化成标量执行，要么需要 mask 机制屏蔽掉不该执行的通道，效率打折。

#### 1.1.4 SIMT：单指令流多线程

SIMT（Single Instruction Multiple Threads）是 NVIDIA 为 GPU 发明的执行模型，可以理解为"**披着多线程外衣的 SIMD**"，但对程序员呈现的编程模型完全不同：

- 在 SIMD 里，程序员写的是**一条对向量操作的指令**（`vaddps ymm0, ymm1, ymm2`）。
- 在 SIMT 里，程序员写的是**标量的、看起来像单线程的代码**（`c = a + b`），硬件把这份代码分发给一组线程（NVIDIA GPU 中是 32 个线程，即一个 Warp），这一组线程**在硬件层面上被同一个指令译码/发射单元以锁步（lockstep）方式驱动**，本质上等价于执行了一条 32 路宽的 SIMD 指令，但看起来是 32 个独立线程各自执行自己的标量程序。

这个"伪装"是 SIMT 最重要的设计价值：它极大降低了并行编程的心智负担。程序员不需要手动向量化，只需要写"每个线程做什么"，硬件负责把这些标量线程组织成 SIMD 执行。这也是为什么 GPU 编程模型能够支持分支（if/else）——每个线程逻辑上是独立的，只是硬件在物理上把它们捆在一起执行（细节见 1.4 节的 Divergence/Reconvergence）。

| | SIMD | SIMT |
|---|---|---|
| 编程模型 | 程序员显式操作向量 | 程序员写标量的单线程代码 |
| 并行粒度 | 指令级（一条指令内部并行） | 线程级（多个线程共享一条指令流） |
| 分支处理 | mask，效率随机应变 | Warp 内部 divergence，靠 predication/reconvergence |
| 典型硬件 | CPU 向量单元 (AVX) | GPU SM 内的 Warp |
| 代表 | `vaddps ymm...` | `warp` 中 32 个线程执行 `c = a + b` |

#### 1.1.5 Throughput Processor vs Latency Processor 小结

用一句话总结这一节：**CPU 是"用面积换延迟"的处理器，GPU 是"用并行度换延迟"的处理器**。GPU 之所以能在算力上远超 CPU，本质原因是它把绝大部分芯片面积都花在了 ALU 和支撑海量线程并发的资源（寄存器堆、调度器）上，而不是花在"让单个任务更快"的乱序执行和大 Cache 上。这个设计哲学会在后面每一节反复出现——GPU 硬件的几乎所有结构（Warp、Warp Scheduler、大寄存器堆、层次化 Memory）都是围绕"**如何让海量线程并发、以并行掩盖延迟**"这一个核心目标展开的。

### 1.2 GPU 硬件组成

现代 NVIDIA GPU 的物理结构是一个清晰的层次化树状结构。从大到小：

```
GPU
 └── GPC (Graphics/GPU Processing Cluster)   ×N
       └── TPC (Texture Processing Cluster)   ×N
             └── SM (Streaming Multiprocessor) ×2   （一个 TPC 通常含 2 个 SM）
                   ├── Warp Scheduler ×4（现代架构通常每 SM 4 个）
                   ├── CUDA Core（FP32/INT32 ALU）
                   ├── Tensor Core
                   ├── Register File
                   ├── Shared Memory / L1 Cache（物理上共享同一块 SRAM）
                   ├── LD/ST Unit
                   └── SFU (Special Function Unit)
 └── L2 Cache（GPU 内所有 SM 共享）
 └── Memory Controller
 └── HBM / GDDR（片外显存）
```

#### 1.2.1 GPC（GPU Processing Cluster）

GPC 是 GPU 内部最大的物理分区，可以理解为"一个几乎完整的小 GPU"：每个 GPC 通常拥有自己的光栅引擎（图形场景下）、若干 TPC，在某些架构上甚至有独立的 L1.5 或专属资源。**GPC 是芯片做"可伸缩设计"的最大颗粒度**——NVIDIA 用同一套 GPC 设计,通过增减 GPC 数量,快速衍生出同一代架构里从入门到旗舰的一整个产品线（例如 Ampere 的 GA102/GA104/GA106 只是 GPC/TPC/SM 数量不同）。

#### 1.2.2 TPC（Texture Processing Cluster）

TPC 是 GPC 内部的下一级分区，历史上因为承载纹理单元而得名。在现代架构中，一个 TPC 通常包含 **2 个 SM** 并共享一部分资源（如指令缓存或纹理单元）。到了 Blackwell，TPC 的地位进一步提升——引入了 **CTA Pair（成对协作线程块）**机制，同一 TPC 内两个 SM 可以通过专用的 TPC 内通信网络直接共享 Tensor Core 的操作数，减少重复的数据搬运（这是第五部分会详细讲的内容）。

#### 1.2.3 SM（Streaming Multiprocessor）：GPU 真正的计算心脏

SM 是 CUDA 编程模型能够感知到的最小硬件调度单元（一个 Block 只能被调度到一个 SM 上执行，见 1.3 节）。一个 SM 内部大致包含：

- **若干个 Warp Scheduler**（现代架构通常是 4 个，每个 SM 划分为 4 个 Processing Block/Partition，每个 Partition 各自有一个 Warp Scheduler + Dispatch Unit）。
- **CUDA Core**：执行 FP32/INT32 等标量运算的 ALU，数量在各代架构中不断变化（如 Ampere 消费级每 SM 128 个 FP32 core）。
- **Tensor Core**：专门做矩阵乘加的硬件单元，从 Volta 开始出现，逐代增强（第五部分详细展开）。
- **Register File**：巨大的片上寄存器堆（现代架构普遍是每 SM 64K 个 32-bit 寄存器 = 256KB），由所有驻留在该 SM 上的线程共享划分。
- **Shared Memory / L1 Cache**：一块可配置的高速 SRAM，物理上 L1 和 Shared Memory 共用同一片存储（从 Volta 开始），可以按需分配比例。
- **LD/ST Unit**：处理访存指令的地址生成和收发。
- **SFU（Special Function Unit）**：处理超越函数（sin/cos/exp/rsqrt 等）和插值等特殊运算。

SM 是本教程后面几乎所有内容的物理载体——Warp 调度、寄存器分配、Shared Memory bank conflict、Tensor Core 流水线，全部发生在 SM 内部。

#### 1.2.4 Warp Scheduler：SM 内部的"大脑"

一个 SM 上可以同时驻留几十个 Warp（例如 64 个），但 SM 内的计算单元（CUDA Core、Tensor Core、LD/ST Unit）数量是有限的，不可能让所有 Warp 真正同时执行指令。**Warp Scheduler 的职责就是每个时钟周期，从当前驻留在其 Partition 内的、且已经"就绪"（下一条指令的操作数已经准备好、没有未满足的依赖）的 Warp 中，挑选出一个（或多个，见 Dual Issue）发射指令去执行。**

这是理解 GPU 高吞吐的关键机制：Warp Scheduler 本质上是一个**零开销的硬件线程切换器**。CPU 的线程切换需要保存/恢复上下文（有开销，通常是微秒级），而 GPU 的每个 Warp 的寄存器都是独占、常驻在寄存器堆里的（不需要 save/restore），所以 Warp Scheduler 可以做到**每个周期都切换到不同 Warp 而没有额外开销**，这正是延迟隐藏（Latency Hiding，见 1.6 节 Roofline 前的铺垫）能够生效的物理基础。

#### 1.2.5 Register File：为什么 GPU 需要这么大的寄存器堆

正因为线程切换零开销依赖"每个线程的寄存器都独立且常驻"，GPU 的寄存器堆必须做得非常大。现代架构典型配置是**每个 SM 64K 个 32-bit 寄存器（256KB）**，由同时驻留在该 SM 上的所有线程平分。如果一个线程用了 64 个寄存器，一个 SM 理论上最多能同时驻留 `65536 / 64 = 1024` 个线程；如果每个线程用了 128 个寄存器，能驻留的线程数就砍半——**寄存器使用量直接决定了 Occupancy（占用率）**，这是第二部分会展开的重要话题。

#### 1.2.6 Shared Memory：程序员可控的片上暂存区

Shared Memory 是一块由程序员显式管理的高速 SRAM，物理延迟和 L1 Cache 接近（几十个周期），但**不是缓存**——它不会被自动换入换出，数据的存在与否完全由程序员的代码决定。这一点和 CPU 完全没有对应物：CPU 的 Cache 是硬件透明维护的，程序员感知不到；而 GPU 的 Shared Memory 更像是"软件管理的 scratchpad"，其存在的意义在第三部分会详细展开——本质上是为了让 Block 内的线程可以互相共享中间数据，避免反复访问慢得多的 Global Memory。

#### 1.2.7 L1 / L2 / HBM：层次化片外访存体系

- **L1 Cache**：SM 私有，从 Volta 开始与 Shared Memory 共享同一块物理 SRAM（可配置切分比例），容量在几十 KB 到几百 KB 之间随代际增长。
- **L2 Cache**：GPU 内所有 SM 共享的最后一级片上缓存，容量随代际大幅增长（Ampere A100 40MB，Hopper H100 50MB，Blackwell 更大），是缓解"算力增长远快于显存带宽增长"这一根本矛盾的重要手段。
- **HBM（High Bandwidth Memory）**：数据中心级 GPU 使用的片外显存，通过 2.5D/3D 封装堆叠多层 DRAM Die，用极宽的位宽（几千位）换取远超传统 GDDR 的带宽（HBM3 单卡可达 3TB/s 以上）。消费级 GPU 一般用 GDDR6/GDDR6X/GDDR7。

这几层构成了本教程反复提及的**Memory Hierarchy**（详见 1.5 节），其存在的根本原因只有一个：**片外显存带宽的增长速度，远远跟不上片上算力的增长速度**（这个"剪刀差"是贯穿全书 Part 3/Part 5/Part 10 的核心矛盾）。

### 1.3 GPU 执行模型：Grid / Block / Warp / Thread

上一节讲的是硬件的"物理"组织，这一节讲的是 NVIDIA 为了让软件能映射到这套硬件而设计的**逻辑**执行模型。注意：这里先不涉及 CUDA C++ 语法，只讲抽象概念，具体 API 在第二部分展开。

```
逻辑层次(软件视角)              物理层次(硬件视角)
─────────────────              ─────────────────
Grid  (整个kernel启动的所有线程)   → 映射到整个 GPU
  └── Block (线程块)              → 映射到一个 SM（一个 Block 只能在一个 SM 上运行，不能跨 SM）
        └── Warp (32线程一组)      → 映射到 SM 内的一个 Warp Scheduler 分区
              └── Thread (线程)   → 映射到一个 CUDA Core 通道(lane)
```

- **Thread**：最小的逻辑执行单位，每个 Thread 有自己的程序计数器（自 Volta 起）、寄存器、局部变量。
- **Warp**：硬件调度和执行的最小颗粒度，固定由 **32 个连续 Thread** 组成（原因见 1.4 节）。Warp 内的线程以 SIMT 方式锁步执行。
- **Block（Thread Block / CTA, Cooperative Thread Array）**：一组 Warp 的集合，Block 内的线程可以通过 Shared Memory 通信、通过 `__syncthreads()` 同步。**一个 Block 会被完整地调度到一个 SM 上，且在其生命周期内不会被迁移到其它 SM。**
- **Grid**：一次 kernel 启动所产生的所有 Block 的集合，代表整个并行计算任务。

为什么设计成这四层，而不是两层（比如只有 Grid 和 Thread）？根本原因是**硬件资源的物理边界需要在逻辑模型中体现出来**：

- Block 之所以存在，是因为 Shared Memory 和 `__syncthreads()` 这种"低延迟通信/同步"只能在**同一个 SM 内部**高效实现（跨 SM 通信必须绕道 L2/Global Memory，代价高几个数量级）。所以"能互相高效通信的线程集合"必须被限定在一个 SM 的范围内——这就是 Block。
- Warp 之所以存在，是因为 SM 内部的指令发射硬件（译码器、Dispatch Unit）不可能对每个线程单独发射指令（面积和功耗都负担不起），必须把线程打包成组，用一条指令驱动一组——这就是 Warp。
- Grid 之所以存在，是因为一个计算任务的规模往往远超单个 SM 能容纳的线程数，需要把任务切分成多个 Block，由 GPU 的 Block 调度器（GigaThread Engine）动态地分发到所有空闲的 SM 上，从而实现跨 SM、跨 GPU 规模的可伸缩性（同一份代码，不用修改就能在小 GPU 和大 GPU 上都跑，只是 Block 被分发到的 SM 数量不同）。

这一节结尾直接回答用户在第二部分开头提出的问题（提前给出结论，具体展开见第二部分）：

- **为什么 Block 不能跨 SM？** 因为 Block 内线程要共享同一块物理 Shared Memory、要用 `__syncthreads()` 做低延迟同步，而 Shared Memory 是 SM 的私有片上资源，不存在"跨 SM 共享的 Shared Memory"这种硬件（Hopper 的 Cluster/DSM 某种程度上突破了这一点，但那是 Block 之上的新层级，不是让 Block 本身跨 SM，详见第十部分）。
- **为什么 Warp 固定 32 线程？** 详见 1.4 节，本质上是 SM 内部 SIMT 硬件通道数（lane 数）与调度开销之间权衡的结果。

### 1.4 Warp 执行机制：SIMT、Divergence、Reconvergence

#### 1.4.1 SIMT 执行的物理实现

一个 Warp 的 32 个线程，在硬件上共享**同一个程序计数器（在 Pre-Volta 架构上）**和**同一条被取出、译码、发射的指令**。SM 内的 ALU 通道是按 Warp 宽度组织的，一条指令一旦被发射，就会驱动 32 个（或该架构分区内实际拥有的 ALU 数量对应的）计算通道，在几个周期内完成整个 Warp 的运算。

**为什么恰好是 32？** 这是一个纯粹的工程权衡结果，并没有什么"神圣"的数学原因：
1. 太小（比如 8 或 16）：指令发射、译码的开销相对计算收益占比过高，SIMT"打包"带来的效率提升不明显；同时管理更多更小的 Warp 会增加调度器复杂度。
2. 太大（比如 64 或 128）：Divergence（分支分歧）造成的效率损失会更严重——一个 Warp 内只要有一个线程走不同分支，整个 Warp 都要为这两条路径分别执行，Warp 越大，"恰好所有线程都走同一路径"的概率越低。
3 . 32 是 NVIDIA 在多代硬件实测中权衡"指令发射效率"与"分支分歧代价"后选定的数字，并且历史上一直保持稳定（从 Tesla 架构到 Blackwell 都是 32），使得整个软件生态（PTX、SASS、编译器、几十年的 kernel 代码）都可以稳定地基于这个假设构建，不用为兼容不同 Warp 宽度而设计"可变宽度"这种复杂机制。

补充一点物理细节：不同架构中，一个 SM 分区（Partition）实际拥有的 FP32 ALU 数量不一定等于 32（例如某些架构一个 Partition 只有 32 个 FP32 core，也有的更多或更少），当 ALU 数量小于 Warp 宽度时，一条 Warp 指令需要分多个周期"流过"这批 ALU 才能全部完成——这不影响 Warp 作为调度和指令发射颗粒度固定为 32 这一事实，只是执行延迟上的差异。

#### 1.4.2 Divergence（分支分歧）

当 Warp 内的线程执行到条件分支（如 `if (threadIdx.x < 16) { A(); } else { B(); }`）且分支结果因线程而异时，就会发生 **Warp Divergence**：

```
Warp (32 threads)
  线程 0-15:  条件为真，需要执行 A()
  线程 16-31: 条件为假，需要执行 B()

硬件的处理方式（Pre-Volta，基于 SIMT 栈）：
  第 1 步：屏蔽掉 16-31，让 0-15 执行 A()  （16-31 空闲，被 predicate mask 掉）
  第 2 步：屏蔽掉 0-15，让 16-31 执行 B()  （0-15 空闲）
  第 3 步：Reconverge，全部 32 线程继续往下执行共同代码
```

关键结论：**Divergence 不会产生错误结果，但会造成性能损失**——因为两条分支路径是**串行执行**的，总耗时约等于两条路径耗时之和，而不是取较慢的那条。这也是为什么"避免 Warp 内的分支分歧"是最基础的 CUDA 性能优化原则之一（具体优化手法见第十一部分）。

#### 1.4.3 Reconvergence（重新收敛）与 SIMT 栈

Pre-Volta 架构使用**基于硬件栈的 SIMT 重新收敛机制**：编译器在生成代码时会插入特殊的控制流指令（如 `SSY`/`SYNC` 在旧 SASS 中），硬件维护一个栈来记录"哪些线程在哪个分支路径、什么时候需要重新汇合"。这个机制隐含一个重要假设：**分支会在某个编译期可确定的汇合点重新收敛**，且这个过程完全由硬件自动管理，程序员无法干预、也无法让分支双方线程在收敛点之前进行数据交换（因为它们根本没有"同时"执行过）。

#### 1.4.4 Volta 独立线程调度（Independent Thread Scheduling）

Volta 架构对 SIMT 执行模型做了一次重要修改：**给每个线程独立的程序计数器（PC）和调用栈（Stack）**，不再是整个 Warp 共享一个 PC。这解决了 Pre-Volta 模型的一个根本缺陷——分支两侧的线程无法互相通信、等待或传递消息（例如经典的"生产者-消费者"式细粒度同步、或者持锁/解锁算法在 Pre-Volta 上很容易死锁，因为持锁线程可能永远等不到因分支分歧被卡住的解锁线程执行）。

Volta 的做法是：硬件仍然尽量把执行相同代码路径的线程组织在一起以 SIMT 方式高效执行（由一个"收敛优化器"负责），但线程之间的执行顺序不再被"必须锁步"这个假设束缚——线程可以在细粒度上交替执行、互相等待。程序员如果需要"这些线程现在必须看到彼此的最新数据"这种保证，必须显式调用 `__syncwarp()`，而不能像 Pre-Volta 时代那样依赖隐式的锁步假设。这也是为什么从 CUDA 9 开始，`__shfl`、`__ballot` 等 Warp 内建函数全部加上了 `_sync` 后缀并要求显式传入参与线程的 mask——**旧的"隐式 Warp 同步"假设在 Volta 之后不再安全**。

#### 1.4.5 为什么理解 Divergence/Reconvergence 很重要

这不是一个只在写 if-else 时才用得到的边角知识——PTX 层面的 `vote.sync`、`match.sync`（第六部分）、Cooperative Groups 的 tiled partition（第七部分）、以及 Warp 内规约（reduce）、扫描（scan）算法（第十二部分）都直接建立在"Warp 是 SIMT 执行、线程间通信需要显式同步"这一底层机制之上。

### 1.5 GPU Memory Hierarchy（概览）

这一节先建立整体地图，详细的"为什么每一层存在、怎么用、怎么优化"留给分量最重的第三部分。这里只回答一个问题：**GPU 的存储为什么要分这么多层？**

```
                延迟增大 / 容量增大 / 带宽降低
        ┌──────────────────────────────────────►
Register  →  Shared Memory  →  L1 Cache  →  L2 Cache  →  Global Memory (HBM/GDDR)
(每线程私有) (每 Block 共享)   (每 SM 私有)  (全 GPU 共享)   (全 GPU 共享，片外)
 ~0 cycle    ~20-30 cycle      ~20-30 cycle   ~200 cycle      ~400-800 cycle
 数 KB/线程    数十~数百 KB/SM    数十~数百KB/SM   数十 MB        数十 GB
```

此外还有两类"特化"的存储路径，服务于特定访问模式：

- **Constant Memory**：只读、全 GPU 共享，专为"所有线程读同一个地址"这种广播式访问模式优化，有专用的常量缓存（Constant Cache）。
- **Texture Memory**：只读，专为图形学中常见的 2D/3D 空间局部性访问模式优化（相邻像素访问相邻内存位置），有专用的纹理缓存，并支持硬件插值。在通用计算里，其只读+空间局部性优化的特性偶尔会被 GPGPU kernel 利用（如 `__ldg` 走只读数据路径）。

分层存在的根本原因，和 CPU 的 Cache 层次结构逻辑一致——**在物理上，"容量大"和"速度快"这两个目标不可兼得**（大容量存储的寻址、驱动电路开销更大，物理距离计算单元更远），因此需要用多级、容量递增而速度递减的存储形成金字塔，让频繁访问的数据尽量停留在金字塔顶端。

但 GPU 相比 CPU 有一个本质不同点：**Shared Memory 是程序员显式管理的，不是硬件自动缓存**。这是因为 GPU 面对的负载模式（大规模规整的数据并行计算，如矩阵分块）往往有清晰、可预测的数据复用模式，程序员/编译器完全能够提前知道"哪些数据接下来会被反复用到"，所以让程序员显式控制能获得比硬件自动缓存策略（如 LRU）更优的效果——这正是第三部分要重点讨论的内容。

### 1.6 Roofline 模型：算力和带宽，谁才是瓶颈？

#### 1.6.1 核心思想

Roofline 模型是分析一个计算 kernel 性能上限的经典工具，核心思想极其简单：**任何计算任务的实际性能，同时被"算力上限"和"带宽上限"这两条"屋顶线"约束，取决于任务本身的访存/计算比例，实际达到的性能不可能超过这两条线中较低的那一条。**

```
性能 (FLOPS)
   ▲
   │                    ┌───────────────────  算力上限 (Peak FLOPS)
   │                 ／
   │              ／          <- Compute Bound 区域
   │           ／
   │        ／     <- 斜线部分：带宽上限 (Peak Bandwidth × AI)
   │     ／
   │  ／      <- Memory Bound 区域
   └──────────────────────────────────►
                          算术强度 Arithmetic Intensity (FLOPs/Byte)
                    (转折点通常称为 Ridge Point)
```

#### 1.6.2 Arithmetic Intensity（算术强度）

算术强度（AI）定义为：

```
AI = 总浮点运算次数 (FLOPs) / 总访存字节数 (Bytes)
```

它衡量的是"每从显存搬一个字节数据，能配套做多少次计算"。AI 越高，说明这个 kernel 越"划算"——搬运一次数据可以反复使用，计算单元有更多机会被喂饱。

#### 1.6.3 Compute Bound vs Memory Bound

- **Memory Bound（访存受限）**：AI 较低，kernel 的瓶颈是数据搬运速度，即使算力单元再强也无济于事，因为大部分时间都在"等数据"。典型例子：向量加法（`c[i] = a[i] + b[i]`，1 次加法配 2 次读 1 次写，AI 极低）、Element-wise 算子、朴素的 Attention softmax。
- **Compute Bound（算力受限）**：AI 较高，数据一旦搬到片上就能反复使用做大量计算，瓶颈是 ALU/Tensor Core 的算力。典型例子：大矩阵乘法（GEMM，尤其是方阵规模足够大时，数据复用率极高）。

#### 1.6.4 Roofline 模型为什么是 GPU 优化的第一性原理工具

Roofline 模型的价值在于：**它告诉你在优化一个 kernel 之前，应该先搞清楚"我到底该往哪个方向使劲"**。如果一个 kernel 是 Memory Bound（大部分 GPGPU 通用 kernel 其实都是），那么无论怎么减少计算指令数、用更快的 ALU，都不会有明显提升，真正该做的是减少访存量、提高访存效率（合并访存、复用 Shared Memory、减少精度）；反过来如果是 Compute Bound（典型如大规模 GEMM/卷积），优化重点应该是提高 ALU/Tensor Core 利用率（减少指令开销、更好的流水线、更高效的 Tensor Core 指令）。

这个模型也直接解释了本教程后续大部分内容存在的意义：

- 第三部分讲的 `cp.async`、TMA 等技术，本质上都是在**同一算力水平下，想办法把 Ridge Point 往左推**（用更少、更高效的搬运方式获得同样的数据，等效于提高有效带宽利用率，或者腾出原本用于搬运数据的计算资源）。
- 第五部分讲的 Tensor Core 演进，本质上是在**不断抬高算力上限（Peak FLOPS）这条屋顶线**，而这条线抬得越高，Ridge Point 就越往右移，越来越多原本"算力受限"的任务变成了"访存受限"——这正是 Part 10 反复强调的"算力增长远快于带宽增长"矛盾的量化体现，也是为什么每一代新架构都要在访存搬运机制上做文章的根本原因。

#### 1.6.5 小结：Part 1 应该建立的直觉

读完这一部分，你应该能够脱离任何 CUDA 语法，仅凭硬件结构图就回答：

- 为什么 GPU 用海量简单核心而不是少量复杂核心？（吞吐量优化 vs 延迟优化）
- 为什么 SM 是软件能感知到的最小硬件单元？（Block 不能跨 SM，因为 Shared Memory/同步是 SM 私有资源）
- 为什么 Warp 是 32？（指令发射效率与分支分歧代价的权衡）
- 为什么会有 Divergence？它的代价是什么？
- GPU 的存储为什么要分好几层，Shared Memory 又为什么是"程序员管理"而不是"硬件自动缓存"？
- 给定一个计算任务，怎么用 Roofline 判断它的瓶颈在哪、该往哪个方向优化？

带着这些直觉，我们才能进入第二部分——看软件（CUDA 编程模型）究竟是如何精确地映射到这套硬件之上的。
