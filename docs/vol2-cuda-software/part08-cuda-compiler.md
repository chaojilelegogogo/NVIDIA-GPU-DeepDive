# 第八部分 CUDA 编译器

> 很多人不学这部分，但它非常重要——不理解编译流程，你就无法解释"为什么同样的 CUDA 代码在不同编译选项下生成完全不同的 SASS"，也无法理解为什么一个 kernel 能在还没发布的新 GPU 上运行（JIT）。这一部分把 CUDA → PTX → SASS 这条链路上，编译器每一步具体做了什么摊开来讲。

## 8.1 整体编译流程

```
                  ┌───────────────────────────────────────────┐
  .cu 源文件  →   │                    nvcc                     │  →  可执行文件 / fatbin
                  │  (host代码 + device代码分离处理的驱动程序)      │
                  └───────────────────────────────────────────┘
                              │                    │
                       host 代码路径           device 代码路径
                              │                    │
                       gcc/cl/clang            cicc (前端: CUDA C++ → PTX)
                       (普通 C++ 编译)                │
                              │                    ptxas (PTX → SASS, 生成 cubin)
                              │                    │
                              └──────────┬─────────┘
                                         ▼
                                   fatbinary（把多个架构的 cubin + PTX 打包进一个 fatbin）
                                         ▼
                              链接进最终可执行文件 / 动态库
```

## 8.2 `nvcc`：编译流程的总调度者

`nvcc` 本身不是一个单一的编译器，而是一个**驱动程序（driver）**，它的核心工作是把 `.cu` 文件中的代码按 `__host__`/`__device__`/`__global__` 标注分离成主机代码和设备代码两条路径，分别调用不同的底层工具链处理，最后把结果重新粘合到一起。这也是为什么一个 `.cu` 文件里能同时写 C++ 主机逻辑和 CUDA Kernel，且两者可以用 `<<<>>>` 语法无缝调用——这套语法糖背后是 `nvcc` 在预处理阶段做的源码转换和拆分。

## 8.3 `cicc`：CUDA 前端，C++ → PTX

设备端代码首先经过 `cicc`（基于 LLVM 的 NVIDIA 前端编译器）处理：完成 C++ 模板实例化、内联展开、常见的高层优化（如循环展开、常量传播），最终生成 **PTX 汇编文本**。这一步生成的 PTX 是"**架构无关**"的（准确说是面向一个虚拟计算能力，如 `compute_80`，而非具体的物理 SASS 目标 `sm_80`），因为 PTX 本身是虚拟 ISA，同一段 PTX 理论上可以被面向不同实际架构的 `ptxas` 重新编译。

## 8.4 `ptxas`：PTX → SASS，真正决定性能的一步

`ptxas` 是把 PTX 编译成特定 GPU 架构真正能执行的 SASS 机器码（打包为 cubin）的工具，也是本教程第九部分要深挖的"高级优化魔法"发生的地方：

- **寄存器分配（Register Allocation）**：决定每个虚拟寄存器（PTX 层面数量不受限）如何映射到物理寄存器（数量受限，最多 255/线程），分配策略直接决定 Occupancy。
- **指令调度（Instruction Scheduling）**：重排指令顺序，尽量把有依赖关系的指令拉开距离（填充无关指令进去），减少因为等待 Scoreboard/Stall Count 造成的空转（第四部分讲的调度硬件，正是 `ptxas` 生成的调度信息在运行时被消费的对象）。
- **控制码生成**：为每条 SASS 指令计算 Stall Count、Yield Flag、Barrier 读写掩码、Reuse Flag（第四、九部分详述）。
- **窥孔优化（Peephole）、指令选择**：把 PTX 中较通用的指令模式，匹配成目标架构上更高效的等价 SASS 指令序列。

**编译目标参数（`-arch`/`-code`）非常关键**：

```bash
# -arch=compute_XX 决定 cicc 生成 PTX 时假设的虚拟架构能力（决定能用哪些语言特性/PTX指令）
# -code=sm_XX      决定 ptxas 生成 SASS 时的具体目标物理架构

nvcc -arch=compute_90a -code=sm_90a  kernel.cu   # 只生成 Hopper 专属 SASS，无法在其它架构运行
nvcc -gencode=arch=compute_80,code=sm_80 \
     -gencode=arch=compute_90a,code=sm_90a \
     kernel.cu                                    # 同时生成多个架构的 SASS，运行时按实际 GPU 自动选择
```

## 8.5 Fatbin：一份文件，多份架构代码

**Fatbin（Fat Binary）** 是把针对多个不同 `sm_XX` 编译出的 cubin，以及一份或多份 PTX（作为 JIT 兜底，见 8.7 节），打包进同一个二进制容器的格式。程序运行时，CUDA Driver 会检测当前 GPU 的实际计算能力，从 fatbin 中选取匹配的 cubin 加载执行——这正是"同一个可执行文件/动态库，能在 A100/H100/B200 等不同代际 GPU 上都跑起来，且各自用上了针对本架构编译的最优代码"这件事在文件格式层面的实现基础。

## 8.6 Cubin 与 ELF

**Cubin（CUDA Binary）** 是特定架构的、`ptxas` 编译产物，本质上是一个遵循 **ELF（Executable and Linkable Format）** 格式的目标文件——这也是为什么 `cuobjdump`、`nvdisasm` 这类工具可以像分析普通 CPU ELF 文件一样，解析出符号表、段信息，再反汇编出 SASS 指令。Cubin 内部包含每个 Kernel 需要的寄存器数量、Shared Memory 用量、常量内存布局等元信息，这些信息在 Kernel Launch 时会被 Driver 读取，用于第二部分讲的 Occupancy/资源分配计算。

## 8.7 JIT（Just-In-Time）编译

**Why 需要 JIT**：Fatbin 里预编译的 cubin 只能覆盖打包时已知的架构。如果用户的 GPU 比编译这份程序时更新（比如程序是几年前编译的，用户买了一张新架构的显卡），驱动找不到匹配的 cubin，这时就需要退而求其次，用 fatbin 中打包的 **PTX**（虚拟 ISA，前向兼容性由 NVIDIA 保证——同一大版本内新架构的 Driver 总能理解旧版本 PTX），由**驱动内置的 JIT 编译器（本质上也是一份 `ptxas`）在程序运行时现场编译出适配当前 GPU 的 SASS**，编译结果会被缓存到本地磁盘（Compute Cache），避免每次运行都重新 JIT。

这也解释了为什么"只发布 PTX、不发布任何 SASS"的程序，理论上可以在任何未来更新的架构上运行（只是首次运行有 JIT 编译的开销），而"只发布特定架构 SASS、不带 PTX"的程序在更新的架构上会直接报错找不到匹配的设备代码。

## 8.8 Relocatable Device Code（RDC）与设备端链接

默认情况下，`nvcc` 要求一个 Kernel 调用的所有 `__device__` 函数在**同一个编译单元**内可见（便于激进内联优化），这限制了把设备代码拆分到多个 `.cu` 文件、像普通 C++ 那样分别编译再链接的能力。**`-rdc=true`（Relocatable Device Code）** 打开后，允许设备代码像主机代码一样，先各自编译成带有未解析符号引用的目标文件，最后由 `nvlink`（设备端链接器）统一链接，代价是牺牲了跨文件的内联优化机会（链接时优化 LTO 是弥补这一代价的手段）。

## 8.9 LTO（Link Time Optimization，链接时优化）

传统 RDC 模式下，一旦选择分离编译，编译器在编译某个 `.cu` 文件时看不到其它文件里被调用函数的具体实现，无法做跨文件内联。**Device LTO** 让 `nvcc` 在编译阶段先生成一种保留了更多优化信息的中间表示，链接阶段再重新做全局的内联和优化，从而在"允许分离编译、提高构建的模块化程度"和"不牺牲跨文件优化机会"之间取得平衡——这对于 CUTLASS 这类大量依赖模板和跨文件内联优化的高性能库工程实践上很有意义。

## 8.10 CUDA → PTX → SASS：每一步优化的责任划分

| 阶段 | 工具 | 主要优化职责 |
|---|---|---|
| C++ → PTX | `cicc` | 模板实例化、内联、循环展开、常量传播、高层向量化 |
| PTX → SASS | `ptxas` | 寄存器分配、指令调度、控制码/Scoreboard 生成、窥孔优化、架构专属指令选择 |
| 运行时（可选） | Driver JIT | 兜底适配未预编译的新架构；也可能应用某些运行时相关的优化 |

理解这个划分的意义在于：**当你发现生成的 SASS 不符合预期时，知道该往哪个方向排查**——如果是"该向量化的循环没展开"，问题多半在 `cicc` 阶段（检查 `-Xptxas`/`-Xcicc` 编译选项、循环结构是否阻碍了编译器分析）；如果是"寄存器分配/调度不理想导致大量 stall"，需要关注 `ptxas` 阶段（`--maxrregcount`、`-Xptxas -O3`、甚至直接分析/手改 SASS，这是第九部分的内容）。
